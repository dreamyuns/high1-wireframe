2쿠폰번호 구조 및 생성 규칙
쿠폰번호 형식 (12자리)
쿠폰ID(3) + 레벨(1) + 일련번호(6) + 유효번호 난수(2) 예시: AML 1 000001 57 → AML100000157
구성자리수설명
쿠폰 ID3High1이 대행사별 부여하는 식별자(스펙 파일에서 확인)
레벨1상품 구분 (LV.1=대인, LV.2=소인 등)
일련번호6000001~999999, 우리가 순차 발급
유효번호(난수)2일련번호 패턴 노출 방지용 난수
CVX 형식 주의: 참고 엑셀의 CVX-1-XXXXXXXX는 기존 다른 대행사/이전 시스템 형식. 우리는 미사용, 위 12자리 규칙을 따른다.
생성 주체 및 시점
단품: 고객 결제 완료 시 우리 시스템이 자동 생성, High1 사전 등록/통보 불필요, 즉시 고객 전달.
패키지(객실+티켓): ① PMS 객실 예약 완료 → ② 하이원 예약번호 수령 → ③ 쿠폰번호 생성 → ④ High1 신규 API에 예약번호↔쿠폰번호 매핑 등록.
패키지 매핑 API는 현재 High1 미개발. 단품 연동 완료 후 별도 협의.
레벨 구조 / 유니크 규칙
LV.1=대인 / LV.2=소인 / LV.3~8 미사용 예약. 성인·소인 별도 확인 없이 레벨별 상품 목록만 표시.
동일 쿠폰ID+레벨 내 유니크. CANCELED 번호는 재사용 가능, USED 번호는 재사용 불가.
레벨 구성은 카테고리(스키/워터파크)에 따라 상이. 스펙 파일 수령 후 확정.
3쿠폰 스펙 파일 구조
스펙 파일 개요
High1 마케팅팀이 대행사에 제공하는 엑셀. 시트 1개 = 쿠폰 코드(ID) 1개, 한 파일에 대행사/판매유형별 여러 시트 존재.
주요 필드
필드내용
쿠폰코드시트명과 동일. 쿠폰번호 앞 3자리(쿠폰ID)
이용권명상품명 (예: OAT_26성수기_얼리_워터월드)
사용기간 (use_start_date / use_end_date)고객 현장 사용 가능 기간. 2컬럼 관리. 판매기간 미관리.
레벨행별 레벨 구분 (LV.1, LV.2…)
적용금액입금가 (High1에 납부하는 원가)
여신IDHigh1 내부 정산 계정 식별자 (대행사별 상이)
인쇄기간(판매 시작 가능 기간) 미사용 확정. 사용기간(2컬럼)만 관리.
워터월드 2026 성수기 입금가 / 판매유형
LV.1 대인 40,000원 / LV.2 소인 35,000원.
판매유형 3종(얼리·상시·프로모션) — 유형별 쿠폰 코드 상이 → 어드민에서 유형별 별도 스펙 등록.
우리(AllmyTour) 전용 쿠폰 코드를 High1로부터 발급받아야 함 (미결 M-04).
4API 명세 (우리가 구현할 서버)
개요
API 3개(영업장·상품 구분 없이 통합) · HTTP GET · 인증 없음 · HTTPS 미확인(M-01). 기존 규격서의 lift_*/hiww_ent_* 구분 불필요(High1 확정).
(1) 조회 — GET /search?barcode={쿠폰번호}
코드의미처리
DBOK유효·사용 가능SOLD 확인 후 반환
DBER01미존재DB에 없는 번호
DBER02이미 사용됨USED 상태
DBER03취소됨CANCELED 상태
DBER31/32유효기간 이전/경과미발생 처리 (날짜 체크 제거)
(2) 사용처리 — GET /use / (3) 사용취소 — GET /cancel
/use: SOLD→USED (DBOK). 이미 사용(DBER02)·취소(DBER03) 시도 시 오류.
/cancel: USED→SOLD 복원. 현장 실수 취소 전용(High1 POS 오조작 복원), 고객 취소와 무관. 시간 제한 없음. 환불 시 High1 별도 통보 불필요(단품).
날짜 유효성 정책 / API 순서
날짜 유효성 체크 미구현 — DBER31/32 미발생, 날짜 범위는 어드민 표시용. 각 API 독립 동작(조회 없이 사용 단독 호출도 유효).
배경: 운영 중 유효기간 초과 후에도 현장 사용 필요 케이스 반복 발생 → High1 요청.

7재고 관리
재고 = 우리가 발급한 쿠폰 수. High1 별도 재고 관리 없음. 쿠폰 소진 개념 없음. 발급 한도는 우리 어드민에서 내부 제어. 추가 발급 시 High1 요청 불필요(일련번호 이어서 발급).

처리 주체별 흐름
구분처리 방식High1 통보
단품 취소(자동)고객 요청 → 취소정책 기준 자동 환불 (SOLD→CANCELED)불필요

고객 취소 자동화 가능: High1 통보 불필요(DB 상태 변경만) + 취소정책 사전 설정 + 결제 환불 API 자동 호출.
티켓 취소 정책 설정 (S14-B)
어드민 S14-B에서 상품별 직접 입력(수동). 숙소 취소정책(S06-A)과 동일 구조, 단 기준이 이용일(사용일)(숙소는 체크인 기준).
구간: 기준일 셀렉트(3일 이상 전 / 2일 전 / 1일 전 / 당일 24시 이전) + 위약금율(%).
위약금율 표기: 0% = 무료취소(전액환불) / 1~99% = 부분 위약금 / 100% = 환불불가. 1구간 이상 필수, 노쇼 고정행 없음(PO 결정).
구간1: 이용일 3일 이상 전 → 위약금율 0% (무료취소) 구간2: 이용일 2일 전 → 위약금율 50% 구간3: 이용일 당일 24시 이전 → 위약금율 100% (환불불가)
부분 환불
프런트: 부분 환불 불가(수량 일부 취소 미제공). 어드민: 관리자가 S15에서 수동 부분 환불 가능(숙소 예약관리와 동일).

어드민 VOID 처리 (S16)
개별 VOID(행 선택→모달) + 일괄 VOID(체크박스 다중→상단 버튼). 상세 처리 방식은 M-05 High1 답변 후 확정.
High1 답변: VOID는 파일 확인 필요(역으로 파일 송부 요청), 회수는 "사용처리 완료 쿠폰"으로 추정. → 엑셀 파일 송부 후 재확인(M-05).
10장애 처리 정책
High1은 우리 서버 다운 감지 시 현장 서비스 우선 제공 + 복구 후 사용처리 재시도 로직 보유(예외적 운용). 빠른 복구가 우리 최우선 의무. 긴급 연락처는 우리가 High1에 제공(High1이 우리 API 호출 구조).
API 타임아웃 기준값 미확인 (미결 M-02).
11마진 관리 정책
2단 계층 구조
티켓 마진은 카테고리(1뎁스) 단위 마스터 기준 2단 계층. 숙소 마진(시설 단위)과 동일 원칙이며 S11 마진관리에서 숙소/티켓 탭 통합 운영.
카테고리 마진 마스터 (S11 티켓 탭) ← 1뎁스 단위 기본 마진, 변경 시 미설정 상품 즉시 반영 ▼ 상품 개별 마진 (S14-B) ← 개별 설정 시 마스터 오버라이드 / 미설정 시 상속
마진 규칙
마진율(%) 또는 마진금액(정액) 선택. 마진율 -49%~+100%(정수만), 계산 결과 소수점 버림(floor). 음수=할인 / 양수=마크업. 이력 관리 필수(변경일시·변경자·전/후).
날짜별 입금가와 마진의 관계 (날짜지정형)
날짜별 입금가 조정: S14-C에서 날짜별 입금가 조정 가능(숙소 S06과 동일 방식). 마진은 상품 고정(날짜별로 달라지지 않음, S14-B에서 상품 단위 설정). 판매가 = 날짜별 입금가 + 상품 고정 마진.
미결 신규-1: 날짜별 입금가가 실제 High1 납부액인지 확정 필요. 성수기는 별도 스펙 코드일 수 있음.

S13 — 쿠폰 스펙 관리
High1 엑셀 → 우리 CSV 템플릿 변환 후 업로드. 컬럼: coupon_id·category·product_type·ticket_type·level·level_name·price·use_start_date·use_end_date.
데이터 변경은 엑셀 재업로드(덮어쓰기)로 일원화 — 개별 수정·행 삭제 없음. 업로드 결과: 화면 요약 + 상세 리포트(.txt). 재업로드 시 동일 쿠폰ID+레벨 덮어쓰기 확인.
노출 ON/OFF는 운영 토글(데이터와 분리). OFF→연결 S14 상품 강제 미노출 cascade(🔒). 스펙 삭제 없음 — 제거=토글 OFF로 대체.
S14 — 티켓 상품 관리 (2탭)
S14-B 상품 마스터(탭1): 기본정보(상품명 KO/EN·카테고리·연결스펙·노출) · 마진(카테고리 마스터 상속/개별 토글, 레벨별, floor) · 취소정책(이용일 기준, 1구간+필수, 노쇼 없음).
S14-C 날짜 설정(탭2): 날짜방식(오픈형/날짜지정형) · 날짜지정형 달력(사용기간 기준 월 단위) · 날짜별 한도(∞/숫자/0=매진) · 날짜별 입금가 조정 · 커트오프(N일·시간 전, 미설정 시 당일 자정).
미결 신규-2: 날짜지정형 한도 미설정 날짜 기본값 미확정('기간 내 ∞' vs '판매 불가').

PartDigitsDescription

CVX format note: CVX-1-XXXXXXXX in the reference Excel belongs to another agency / legacy system. We do NOT use it — we follow the 12-digit rule above.
Who/When Generates
Single ticket: our system auto-generates on payment completion; no pre-registration/notice to High1; delivered to customer immediately.
Package (room + ticket): ① complete PMS room booking → ② receive High1 booking no. → ③ generate coupon no. → ④ register booking-no.↔coupon-no. mapping via High1's new API.
Package mapping API is not yet developed by High1. To be discussed after single-ticket integration is complete.
Level Structure / Uniqueness
LV.1=adult / LV.2=child / LV.3–8 reserved. No separate adult/child verification — only the level's product list is shown.
Unique within the same coupon ID + level. CANCELED numbers may be reused; USED numbers cannot.
Level composition varies by category (ski/water park). To be confirmed after receiving the spec file.

Ticket Cancellation Policy (S14-B)
Entered per product by admin in S14-B (manual). Same structure as lodging policy (S06-A), but based on use date (lodging uses check-in date).
Tiers: reference-day select (3+ days before / 2 days / 1 day / before 24:00 same day) + penalty rate (%).
Penalty-rate notation: 0% = free cancel (full refund) / 1–99% = partial penalty / 100% = non-refundable. At least 1 tier required, no fixed no-show row (PO decision).
Tier 1: 3+ days before use → penalty 0% (free cancel) Tier 2: 2 days before use → penalty 50% Tier 3: before 24:00 same day → penalty 100% (non-refundable)
Partial Refund
Front: not allowed (no partial-quantity cancel). Admin: manager can process partial refund manually in S15 (same as lodging).

10Failure Handling
On detecting our server down, High1 prioritizes on-site service and retries use-processing after recovery (exceptional operation). Fast recovery is our top duty. We provide an emergency contact to High1 (since High1 calls our API).
API timeout threshold TBD (M-02).
11Margin Management Policy
Two-Tier Hierarchy
Ticket margin uses a category (depth-1) master in a two-tier hierarchy. Same principle as lodging margin (facility-unit); managed under combined Lodging/Ticket tabs in S11.
Category margin master (S11 Ticket tab) ← depth-1 base margin; on change, inheriting products update instantly ▼ Product-level margin (S14-B) ← overrides master if set / inherits if unset
Margin Rules
Choose margin rate (%) or fixed amount. Rate -49% to +100% (integers only), results floored. Negative=discount / positive=markup. History required (timestamp·editor·before/after).
Per-Date Deposit Price & Margin (date-specific)
Per-date deposit adjustment: deposit price can be adjusted per date in S14-C (same as lodging S06). Margin is fixed per product (does not vary by date; set per product in S14-B). Selling price = per-date deposit + fixed product margin.
New issue-1: Confirm whether the per-date deposit equals the actual amount paid to High1. Peak season may use a separate spec code.
