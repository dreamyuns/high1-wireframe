5. 예약 처리 흐름
5-1. PMS 연동 상품 — 신규 예약
1
고객이 프런트에서 상품 선택 → 예약·결제 정보 입력
2
예약 세션 시작 — 15분 타이머 작동. 타임아웃 시 결제 페이지 자동 이탈 + 재고 반환. (백엔드 처리, 어드민 관여 없음)
3
PG 결제 요청
✕
PG 결제 실패 → 에러 알림 표시 + 결제 페이지 유지. 예약번호 미생성. 기록 없음.
4
PG 결제 성공 → API 6(예약 생성) 호출.
백엔드 자동 재시도: 최대 3회 (1초 → 3초 → 9초 간격)
✕
API 6 3회 모두 실패 → 예약실패 상태로 예약번호 생성. 관리자 즉시 알림(긴급). 고객: "처리 오류, 고객센터 문의" 안내 + 결제 금액 환불 예정 문구 표시.
5
API 6 성공 → 예약번호 생성 + 상태: 확정. 고객 예약 확인 이메일 발송.
⚠️ 예약실패 관리자 처리 필수PG 결제는 완료됐으나 PMS 예약 생성 실패. 고객 돈이 빠진 상태이므로 즉시 확인 및 PG 환불 처리 필요. 처리 완료 후 어드민 S10-B에서 [환불 완료 처리] → 상태 취소완료 전환. 전 과정 이력 자동 기록.
5-2. 수기 관리 상품 — 신규 예약
1
고객이 프런트에서 수기 상품 예약·결제 완료
2
예약번호 생성 + 상태: 확정대기. 관리자 알림 발송.
3
관리자가 호텔 직접 확인 후 처리 결정
4
[확정 처리] → 상태: 확정. 고객 확정 이메일 발송.
✕
[거절] → 상태: 취소완료. 환불 처리. 고객 거절 안내 이메일.
5-3. PMS 연동 상품 — 취소 처리 (자동)
1
고객이 프런트에서 취소 요청 + 취소 사유 선택 (필수)
2
API 10 자동 호출 → 위약금(DLFT_APLY_AMT) · 구간명(DFLT_NM) 조회
3A
위약금 0원 (무료 취소): API 7 자동 호출 → 취소 실행 → 환불 처리 → 상태: 취소완료. 취소 확인 이메일 발송. 관리자 개입 없음.
3B
위약금 발생: 고객에게 위약금 금액 + 구간명 안내 화면 표시
4
고객 [취소 동의] → API 7 자동 호출 → 취소 실행 → 환불 (위약금 차감) → 상태: 취소완료. 취소 확인 이메일 발송.
✕
고객 [취소 철회] → 취소 요청 취소. 예약 확정 상태 유지.
⚠️ API 실패 시 관리자 개입API 10 또는 API 7 처리 실패 시 → 취소요청 상태로 보존 + 관리자 즉시 알림. 관리자가 S10-B에서 수동으로 처리.
5-4. 수기 관리 상품 — 취소 처리 (관리자 처리)
1
고객이 프런트에서 취소 요청 + 취소 사유 선택 (필수) → 상태: 취소요청. 관리자 알림 발송.
2
관리자가 S10-B 예약 상세 확인 후 처리 결정
3
[취소 확정] → 환불 처리 → 상태: 취소완료. 취소 확인 이메일 발송.
관리자 강제 취소하이원 측과 사전 협의 완료를 전제로 관리자가 직접 취소 실행. 취소요청 단계 없이 S10-B에서 직접 처리. 이력에 "관리자 강제 취소" 처리자·사유 기록 필수.
5-5. 노쇼 처리
TBD-3 · 처리 방식 확인 필요PMS에서 노쇼 상태코드 수신 가능한 경우: API 8 동기화 시 자동 상태 전환.
수신 불가한 경우: 우리 시스템에서 체크인일 24시 경과 + 확정 상태인 예약을 자동으로 노쇼 전환하는 배치 또는 스케줄러 구현 필요.
노쇼 정책위약금 100%. 환불 의무 없음. 고객 취소 요청 없이 노쇼로 전환된 경우 별도 환불 처리 불필요.

[취소하기]우측 상단 항상 고정PMS 예약취소(API 7) + PG 전액 결제취소 동시 요청 → S10-C 모달에서 최종 확인 후 처리. 예약 상태 취소완료로 전환. 취소완료·노쇼 상태에서는 미표시.
[부분취소]요금정보 섹션 우측PG 부분 결제취소만 단독 처리. 관리자가 금액 직접 입력 → 잔액 자동 계산. 복수 실행 가능. 예약 상태 변경 없음. 결제취소 내역 블록에 누적 기록.
취소하기 vs 부분취소 구분[취소하기]는 예약과 PG 결제를 동시에 종결하는 전체 취소. [부분취소]는 PG 결제 일부만 환불하는 운영 도구 — 예약 상태와 무관하게 언제든 실행 가능.
예약상태 수기 변경
운영 정책예약일시 하단 드롭다운으로 언제든 수기 변경 가능. PMS 연동 예약도 오버라이드 허용 (관리자 책임). [적용] 버튼 클릭 시 반영 (실수 방지). 변경 시 변경이력 자동 기록 (처리자: 관리자 ID).
주의수기 상태 변경은 PMS 실제 상태와 불일치를 야기할 수 있음. 운영 정책으로 관리 필요.

※ API 10 필드명 오타 주의: DLFT_APLY_AMT (DFLT 아님)

5. Reservation Processing Flow
5-1. PMS-Linked Product — New Reservation
1
Customer selects product on frontend → enters reservation & payment info
2
Reservation session starts — 15-min timer activated. On timeout: auto-exit payment page + inventory returned. (Backend only, no admin involvement)
3
PG payment request
✕
PG payment failure → Error alert displayed + stays on payment page. No booking number created. No record.
4
PG payment success → Call API 6 (create reservation).
Backend auto-retry: max 3 times (1s → 3s → 9s intervals)
✕
API 6 fails all 3 times → Create booking number with Booking Failed status. Immediate urgent admin alert. Customer: "Processing error, please contact support" + "Refund pending" notice.
5
API 6 success → Booking number created + status: Confirmed. Confirmation email sent to customer.
⚠️ Booking Failed — Admin Action RequiredPG payment completed but PMS reservation creation failed. Customer's money has been charged — immediate verification and PG refund required. After processing, admin clicks [Refund Complete] in S10-B → status changes to Cancellation Complete. Full process automatically logged.
5-2. Manual Product — New Reservation
1
Customer completes reservation & payment for manual product on frontend
2
Booking number created + status: Confirmation Pending. Admin notification sent.
3
Admin checks with hotel directly and decides on action
4
[Confirm] → status: Confirmed. Confirmation email sent to customer.
✕
[Reject] → status: Cancellation Complete. Refund processed. Rejection notice email to customer.
5-3. PMS-Linked Product — Cancellation (Automated)
1
Customer requests cancellation on frontend + selects cancellation reason (required)
2
API 10 auto-called → retrieves penalty (DLFT_APLY_AMT) · tier name (DFLT_NM)
3A
Penalty = 0 (Free cancellation): API 7 auto-called → cancellation executed → refund processed → status: Cancellation Complete. Cancellation confirmation email sent. No admin involvement.
3B
Penalty applies: Customer shown penalty amount + tier name on notice screen
4
Customer clicks [Agree to Cancel] → API 7 auto-called → cancellation executed → refund (minus penalty) → status: Cancellation Complete. Cancellation confirmation email sent.
✕
Customer clicks [Withdraw Request] → cancellation request cancelled. Reservation remains Confirmed.
⚠️ Admin Intervention on API FailureIf API 10 or API 7 fails → preserve Cancellation Requested status + immediate admin alert. Admin manually processes in S10-B.

1
Customer requests cancellation on frontend + selects reason (required) → status: Cancellation Requested. Admin notification sent.
2
Admin reviews in S10-B reservation detail and decides action
3
[Confirm Cancellation] → refund processed → status: Cancellation Complete. Cancellation confirmation email sent.
Admin Force CancellationPremised on prior agreement with High1. Admin executes cancellation directly — no customer request step. Processed directly from S10-B. Must log "Admin Force Cancel" with processor and reason in change history.

PMS payment = DLFT_APLY_AMT as-is. Difference (margin portion) retained by us.
※ Note: API 10 field name typo — DLFT_APLY_AMT (not DFLT)
